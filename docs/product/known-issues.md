# SimpleRCPv2 已知问题

更新时间：2026-10-06

本文件记录基线明确接受的问题。每项都包含可观察现象、影响范围、当前处理和完整处理方向。开发过程中发现新的可复现问题时，应当在修复代码或接受该问题的同一次提交中更新本文件。

## KI-001 Agent 可能覆盖成员在同一文件中的修改

状态：当前存在。

### 触发过程

1. Agent 读取文件版本 V0。
2. 成员把该文件修改为 V1。
3. Agent 根据 V0 生成 V2，并把 V2 写入项目目录。
4. V2 没有包含成员在 V1 中增加的内容。

### 影响

磁盘最终保存 V2，文件同步层会把 V2 同步到 Yjs。成员的部分修改可能消失。最小 delta 可以保护未变化区域的 CRDT 字符标识，但无法恢复 V2 中已经缺少的内容。

### 基线处理

- Agent run 开始前等待协作文档保存完成，并记录工作区内容与成员 revision。
- run 结束后比较工作区内容，保存新增、修改和删除文件及增删行数。
- 成员和 Agent 在任务期间修改同一路径时，trace 记录 `concurrent_change`。
- run 详情显示文件变化，保留最终磁盘内容供成员检查。

这套处理只能提示风险，无法保证找回已经被覆盖的内容。shell 命令间接修改文件时，trace 事件的粒度也可能不足。

### 完整处理方向

- 在 Agent 第一次读取文件时保存 base 内容与哈希。
- Agent 修改写入独立工作目录。
- run 完成后以 base、成员当前版本和 Agent 版本执行三方合并。
- 无重叠修改自动合并；重叠修改进入明确的冲突处理界面。
- 合并完成前不改变共享项目目录。

## KI-002 外部进程与成员同时写入时采用完成顺序

### 触发过程

终端程序或 Agent 直接写文件时，成员也可能通过 Yjs 修改同一文件。两次写入都发生在项目目录，系统无法阻止外部进程在任意时刻覆盖文件。

### 影响

最终内容由实际完成顺序决定。同步层可以防止旧 watcher 回调再次覆盖较新的 Yjs 内容，但无法推断两次写入的业务含义。

### 基线处理

- 成员更新经过短暂合并后写入磁盘。
- watcher 收到变化后重新读取当前磁盘内容，并使用最小 delta 更新 Yjs。
- 文件系统来源的 Yjs transaction 不会再次写入磁盘。
- 最终内容由成员写入与外部写入的实际完成顺序决定。
- Agent run 对成员并行编辑显示 `concurrent_change`。

### 完整处理方向

与 KI-001 共用独立工作目录和三方合并流程。共享终端产生的外部写入继续使用完成顺序，因为终端命令没有可用的 base 版本信息。

## KI-003 固定忽略路径的变化不会出现在协作界面

`node_modules`、`.git`、`__MACOSX` 和 `.DS_Store` 不进入文件树、浏览器文件接口和 watcher 事件。终端与 OpenCode 仍然可以访问这些路径。

Agent 或命令修改这些路径时，浏览器不会显示文件变化，也不会创建 Yjs 文档。该行为用于控制依赖安装和 Git 操作产生的事件数量。需要查看结果时使用共享终端。

## KI-004 大文本文件可能影响协作性能

超过 1 MiB 的文本文件需要成员确认后才会打开，确认后仍然进入 Yjs 协作编辑。

大文件会增加初始同步、全文读取和 Yjs 更新的数据量。当前提示可以防止成员无意打开生成文件，但不限制确认后的文件大小。需要更高限制时，应当增加分块读取与编辑，并验证多人同步时的内存与传输开销。

## KI-005 服务中断会终止正在运行与排队的 Agent run

状态：当前存在。

服务重新启动时，历史记录中状态为 `running` 或 `queued` 的 run 会改为 `failed`，并记录服务重新启动原因。服务不会自动重新执行任务。历史 run 与 trace 继续保留。

## KI-006 同一项目的 Agent 任务需要排队

状态：当前存在。

基线允许每位成员提交自己的任务，但同一项目同一时间只执行一个 Agent run。运行时间较长时，后续成员需要等待。

该限制用于防止多个 Agent 直接修改同一项目目录。不同项目拥有独立队列，可以同时执行。完整并行方向见 [改进路线 IM-002](./improvement-roadmap.md#im-002-同一项目的-agent-并行执行)。

## KI-007 轻量身份仅适合受信内部环境

服务端不做鉴权。知道 `memberId` 的人可以冒充该成员，终端或 Agent 内部也可以直接调用本机 API。Role 是自行填写的显示标签，所有成员能力相同。项目管理、全局设置、CORS 和未配置根目录限制的导入接口均开放。

平台只适合受信的内部环境，不应部署到公网。内网部署可以由反向代理添加 basic auth，并限制能够访问服务的人员。

## KI-008 共享终端修改文件时没有语义冲突检测

共享终端中的脚本可以直接修改项目文件。watcher 会把最终内容同步到编辑器，但系统无法知道脚本读取了哪个旧版本，也无法执行可靠的三方合并。

基线按照文件写入完成顺序处理。共享终端接收字符流，当前无法可靠判断一条 shell 命令的提交边界，因此终端输入不会等待协作文档写入完成。需要更强保护时，应当让命令在任务工作目录运行，并把文件变化作为变更集合处理。

## KI-009 在线状态保存范围有限

成员写入 `members.json`，聊天消息写入 `chat.json`，文件、终端输入次数、聊天归属与 Agent Activity 写入 `activity.json`。Agent session、run 和 trace 也保存在项目元数据目录中。Server 重新启动后可以恢复这些内容，并通过原 `memberId` 继续 Agent session。

成员在线状态、页面连接、光标、当前文件和终端屏幕只保存在内存中，Server 重新启动后重新建立。运行中或排队的 Agent run 会标记为 `failed`，并保留已有记录与 trace。

## KI-010 OpenCode 或 Provider 故障会导致 run 失败

状态：当前存在。

OpenCode 进程退出、模型服务请求失败、网络中断或达到超时都会使当前 run 失败。队列继续执行下一项，既有 trace 保留。基线不自动重试修改类任务，避免同一任务重复写入文件。
## KI-011 运行隔离的范围

终端和 Agent 仍以服务端系统用户运行，绝对路径可以读取该系统用户有权限读取的其他文件，包括其他项目和仓库根目录的 `.env`。元数据移出工作区只阻止直接使用 `../` 访问，不能提供操作系统级隔离。当前没有 CPU、内存或进程数限制；需要每个项目一个系统用户或容器时，应在部署环境中增加。

OpenCode 进程需要通过 `DEEPSEEK_API_KEY` 调用 Provider，bash 工具会继承这部分环境，因此 Agent 在获得 bash 审批后仍可能看到模型 Key。终端进程不会继承模型 Key。Guard 会把 bash 请求交给服务端策略和审批队列。

## KI-012 历史 session 与工作目录迁移

无法对应当前成员记录的 session 标为历史记录，保留数据，不按显示名认领。移动工作区后，旧 OpenCode `runtimeSessionId` 仍可能关联原目录；历史内容保留，需要继续工作时创建新的 session。

## KI-013 团队 Agent 共享上下文无法区分指令来源

团队 Agent 会把最近的群聊内容作为讨论上下文提供给 Agent。当前上下文记录成员名称与消息文本，模型可能把其他成员留下的指令当成当前任务的一部分。网络加执行和不可逆操作仍会进入 Guard 审批，其他类型的上下文误解需要成员通过新消息说明实际任务。

## KI-014 低权限成员可以打断高权限成员触发的团队 Agent run

团队 Agent 的新消息会取消同一 Agent 的旧 run，取消旧 run 的成员可以拥有较低角色档位。旧 run 的待审批请求会被拒绝，新 run 按新消息触发者的角色重新判定。当前产品决定保留这种行为，以便团队成员及时停止共享 Agent 的错误任务。

## KI-015 未建模的写文件工具

`tar -x`、`unzip`、`docker run -v` 和 `npx` 的具体文件写入行为没有在 Guard 中建立独立的路径模型。这些命令按执行能力处理，可能需要人工审批。需要更精确的范围控制时，应当使用明确的文件编辑工具或命令。
# Guard 限制

guard-v1.3 已修复 G1 到 G5、H1 到 H4、R3-01 到 R3-04、L3-01 与 T-01。terminal 复合命令逐段判定，工作区 Git 恢复命令支持快照，git clean 按不可逆操作处理，package manager 脚本按子命令判定，同一 session 的并发审批先发送 once 再发送 reject，heredoc 正文不参与路径识别，重定向保留原命令能力，普通复合命令不再自动标记 dynamic，git stash 的只读子命令按 read 处理，网络上传文件参数纳入路径分区，OpenCode 的 read、grep、glob、list 读取路径交给 Guard 判定，下载文件后在同一条命令中交给解释器执行会进入网络加执行规则。Guard 拒绝导致的 OpenCode 空响应记录为 blocked_by_guard。

- 成员可以自行填写角色，当前身份系统不会验证角色的真实性。
- exec 类命令（`make`、`npm run`、`python` 脚本、`rg --pre`、`git -c alias`）不做语义分析。
- 交互控制持有者在提示符上留下的半行会与后续命令拼接。
- subagent 可以通过 `task: deny` 规避，当前没有实现子会话审批。
- human-only 模式下 OpenCode 仍会发出 ask，由服务端自动放行，与 `main` 分支行为不同。
- initiator 在审批中途离线不会自动拒绝。
- Monaco 编辑器内的人工编辑不经过 Guard。
- 交互控制期间的按键直接写入 pty，不经过逐次命令判定。
- OpenCode 的 `env`、`printenv` 仍可能通过工具或进程间接读取敏感内容。
- 下载文件与后续执行分处不同命令时，Guard 仍无法建立两次调用之间的关联。
- 同一系统用户下的绝对路径读取没有 OS 沙箱隔离。
- 快照恢复只覆盖快照中的文件，不删除快照之后的新文件。
